# ADR-001: 배포 단위 — 모듈러 모놀리스로 시작한다

- 상태: Accepted
- 날짜: 2026-09-16
- 관련 Phase: 1 (구조), 5 (api/worker 배포 분리)

## 맥락
공고 요구사항에 MSA 이해가 있고, 도메인은 deal / participation / payment / settlement / realtime / search 여섯 경계로 나뉜다.
처음부터 서비스로 쪼갤지, 하나의 배포 단위 안에서 경계만 강제할지 결정해야 한다.

## 선택지
1. **처음부터 서비스 분리** — 경계가 물리적으로 강제됨 / 1단계부터 분산 트랜잭션·네트워크 장애·배포 복잡도를 떠안음. 경계를 잘못 그으면 되돌리기 가장 비쌈
2. **모듈러 모놀리스 + ArchUnit** — 단일 배포, 단일 DB 트랜잭션으로 시작. 경계는 컴파일·테스트로 강제. 분리는 필요할 때 / "MSA 경험" 항목을 문자 그대로 채우지는 못함
3. **무구조 모놀리스** — 가장 빠름 / 경계가 없어 Phase 3 이후 이벤트 분리가 불가능해짐

## 결정
2번. Gradle 멀티모듈로 경계를 나누고 `arch-test` 가 의존 방향을 강제한다.
Phase 5 에서 부하 특성이 다른 `api` 와 `worker` 만 배포 단위를 분리한다 (ADR-009).

## 근거
- 경계를 올바르게 긋는 것이 분리 자체보다 어렵고 중요하다. 분리는 경계가 검증된 뒤에 해야 싸다.
- 모듈 간 통신을 처음부터 "동기 호출은 한 방향, 역방향은 이벤트" 로 제한하면 서비스 분리 시 코드 변경이 어댑터 교체로 국한된다.
- 포트폴리오 관점에서 "왜 쪼개지 않았는가"를 근거와 함께 설명하는 것이 쪼갠 것보다 설계 이해를 더 잘 보여준다.

## 결과
- 얻는 것: Phase 1~4 의 속도, 단일 트랜잭션의 단순함, 검증된 경계
- 잃는 것: 모듈별 독립 배포·스케일링 (Phase 5 에서 api/worker 만 회복)
- 되돌리려면: 모듈 → 서비스 추출 시 `domain` 포트의 infrastructure 어댑터를 HTTP/Kafka 클라이언트로 교체. `api → application → domain` 레이어 규칙이 이를 가능하게 한다.
