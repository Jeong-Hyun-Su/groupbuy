# ADR-012: 딜 검색은 PostgreSQL 로 한다 (Elasticsearch 제외)

- 상태: Accepted
- 날짜: 2026-09-28
- 관련 Phase: 1, 5

## 맥락
설계서 v0.2 는 Phase 5 에 Elasticsearch(Nori 한글 분석, 이벤트 기반 색인)로 딜 목록·검색(UC-02)을 옮길 계획이었다.
이 프로젝트가 증명하려는 것은 결제·정산 정합성, 동시성, 실시간 전파, 이벤트 기반 설계, 운영이다. 검색은 그중 어디에도 들어가지 않는다.
설계서 14장 리스크 표도 범위를 자를 때 Elasticsearch 를 가장 먼저 빼기로 정해 두었다 ("도메인 필연성이 가장 약하다").

## 선택지
1. **Elasticsearch 로 이관** — 한글 형태소 검색, 인기도 정렬 색인 / 색인 동기화(이벤트 컨슈머, 재색인), 클러스터 운영, 로컬 메모리 부담. 증명 대상과 무관한 작업이 1주 가까이 든다
2. **PostgreSQL 유지** — 이미 동작한다 (`DealJpaRepository.search`: 상태 필터, 제목 부분 일치, 마감임박·인기순, 페이지 상한) / 한글 형태소 분석이 없고, 딜 수가 매우 많아지면 `LIKE` 가 느려진다

## 결정
2번. `modules/search` 를 제거하고, 목록·검색은 `deal` 모듈의 DB 조회로 둔다.

## 근거
- 딜 수는 동시에 열린 수천 건 수준을 가정한다. 상태·마감 시각 인덱스(`deals(status, close_at)`)로 필터한 뒤 제목을 부분 일치하면 충분하다
- 이 프로젝트의 부하 대상은 목록 조회가 아니라 참여 폭주·마감·환불이다

## 결과 (트레이드오프)
- 얻는 것: 모듈 하나, 이벤트 컨슈머 하나, 인프라 하나가 줄어든다. 그 시간을 Phase 3(결제 정합성)에 쓴다
- 잃는 것: 한글 형태소 검색, "검색 엔진 운영" 경험
- 되돌리는 조건: 제목 검색 p95 가 목표(설계서 4.1)를 넘거나 형태소 검색 요구가 생기면 `pg_trgm` 인덱스를 먼저 시도하고, 그래도 부족하면 `deal.lifecycle`·`participation.events` 를 구독하는 색인 컨슈머를 추가한다
